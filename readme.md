# Модуль MSSP PIC16F1825 и драйвер I2C для стека PCF8574
## Технический документ: архитектура, реализация, правила сопровождения

Версия: 1.0 (10.11.2026)
Проект: stack_PCF8574 (репозиторий: https://github.com/anaera/stack_PCF8574)
Контекст: часть 2 из 3 — драйвер I2C и обработчик стека PCF8574

---

## 1. Место модуля в проекте

Проект состоит из трёх частей:

1. **Коммуникационная часть** — работа с UART и разработка CANopen-подобной подсистемы (отдельный этап).
2. **Драйвер I2C и обработчик стека PCF8574** — отслеживание и управление цифровыми пинами (этот документ).
3. **Приложение** — управление внешними исполнителями (свет, нагреватели и др.) от многофункциональных кнопок и через межкомпонентное взаимодействие.

Часть 2 реализована, проверена в симуляторе MPLAB по всей длине стека PCF8574 и передаётся в сопровождение в виде, описанном ниже. Выходы на восстановление шины будут полноценно тестироваться после подключения таймеров (следующий этап).

## 2. Аппаратная база

- MCU: **PIC16F1825** (MSSP в режиме I2C Master, аппаратно).
- Ведомые: до 8 чипов **PCF8574** (адреса 0x20–0x27, в EEPROM хранятся 7-битные адреса, сдвиг на 1 бита R/W выполняется программно).
- Шина: SCL — RC0, SDA — RC1, подтяжки внешние; скорость 100 кГц (SSP1ADD = 39 при Fosc = 16 МГц: Fi2c = Fosc/(4*(SSP1ADD+1))).
- Тактирование: INTOSC 16 МГц (OSCCON = 0x78), PLL выключен.

### Ключевые регистры MSSP и биты, задействованные в драйвере

| Регистр | Биты | Роль в драйвере |
|---|---|---|
| SSP1CON1 | SSPEN, SSPM<3:0> = 1000 | Включение модуля, режим I2C Master |
| SSP1CON1 | WCOL | Коллизия записи в SSP1BUF (сбрасывается программно) |
| SSP1CON2 | SEN, PEN, RCEN, ACKEN | Стартовые/стоповые/приёмные/ACK-сигналы; самосбрасываются по завершении |
| SSP1CON2 | ACKSTAT, ACKDT | Ответ ведомого / значение ACK мастера |
| SSP1STAT | S, P, SMP | Состояние шины (начало/конец пакета), скорость slew-rate |
| SSP1BUF | — | Буфер обмена (запись и чтение) |
| SSP1ADD | — | Делитель скорости |
| PIR1/PIE1 | SSP1IF / SSP1IE | Флаг/разрешение события MSSP |
| PIR2/PIE2 | BCL1IF / BCL1IE | Флаг/разрешение коллизии шины (bus collision) |

Сверка манипуляций с битами по даташиту PIC16F1825 выполнена; ошибок в именах и адресации битов не найдено. Отдельно проверена семантика битов конфигурации: в XC8 имена инвертированы относительно регистровых битов (например, `PWRTE = OFF` = «таймер включения отключён»), комментарии в config.h точны.

## 3. Слои и файловая структура

```
main.c           — точка входа, ISR, главный цикл
initChip.c       — тактирование, WDT, порты
i2c_driver.c     — автомат транзакции (ядро части 2)
i2c_driver.h     — публичный API драйвера, дескриптор, коды ошибок
i2c_core.h       — аппаратный слой регистровых операций (реальное железо)
i2c_core_sim.h   — фейковый слой (симуляция ведомых, включается при I2C_SIM)
update.c/.h      — обработчик стека PCF8574: цикл чтения/записи, теневая модель
epp_update.h     — дескриптор чипа (адрес, начальное состояние, инверсия, направления, кнопки)
epp_full.h       — полный образ EEPROM (8 чипов)
epp.c            — инициализация EEPROM-образа
config.h         — конфигурационные биты
```

Выбор слоя выполняется макросом:

```c
#ifdef I2C_SIM
#include "i2c_core_sim.h"
#else
#include "i2c_core.h"
#endif
```

**Принцип слоения:** main.c не знает внутренних состояний драйвера; ISR — «глупый», только проверка разрешений/флагов и вызов движка; вся логика — в драйвере. Слой i2c_core — единственное место, где лежат манипуляции с регистрами MSSP.

## 4. Публичный API драйвера

### 4.1 Дескриптор транзакции

```c
typedef struct {
    uint8_t adr;              // байт адреса с битом R/W (уже сдвинут на 1)
    void (*exitFunc)(void);   // колбэк завершения транзакции
    error_e error;            // код ошибки операции
    uint8_t value;            // данные (запись) / результат (чтение)
} i2c_api_t;
```

Коды ошибок: `I2C_OK`, `I2C_ADDR_ERR` (NACK на адрес), `I2C_DATA_ERR` (NACK на данные), `I2C_BUFF_ERR` (WCOL), `I2C_FATAL_ERR` (коллизия шины, BCL).

### 4.2 Жизненный цикл транзакции (контракт)

1. Приложение заполняет `adr`, `value`, `exitFunc`, `error = 0`.
2. Вызов `I2C_Start(&d)`: проверяется готовность шины (`BusReady`), при успехе — устанавливается дескриптор, `state = _AFTER_SEND_START`, взводится `SEN`. Возврат `true` = транзакция принята; завершение будет уведомлено через `exitFunc`.
3. Движок ведёт транзакцию из ISR по шагам автомата.
4. По завершении (успех или любая ошибка) единственная точка выхода — `do_EXIT()`: вызов `exitFunc()`, обнуление `exitFunc` и `ptr_i2c`, затем `state = _IDLE` (последней операцией, как положено ISR-ветке).
5. Приложение в колбэке читает `error` (значение — отдельная переменная, не через дескриптор) и принимает решение о следующем шаге.

**Дескриптор расходуем:** после завершения транзакции указатель и колбэк обнулены — повторное использование требует нового `I2C_Start`. Это структурно исключает случайный доступ к «мёртвому» дескриптору.

## 5. Автомат транзакции

### 5.1 Состояния

```
_IDLE, _AFTER_SEND_START, _AFTER_SEND_ADDR, _AFTER_SEND_DATE,
_AFTER_SEND_RxEN, _AFTER_SEND_NAK, _AFTER_SEND_STOP
```

### 5.2 Переходы

Запись: IDLE → START → ADDR → DATE → STOP → EXIT
Чтение (однобайтовое): IDLE → START → ADDR → RxEN → NAK → STOP → EXIT

Ветки ошибок: NACK на адрес → STOP/EXIT (ADDR_ERR); NACK на данные → STOP/EXIT (DATA_ERR); WCOL на этапе START или ADDR → STOP/EXIT (BUFF_ERR); BCL в любой момент → немедленный FATAL_ERR и EXIT без завершения шины (шину разрулит Recover при следующем Start).

### 5.3 Семантика шагов

- `_AFTER_SEND_START` — флаг снятия SEN; отправка байта адреса в SSP1BUF; проверка WCOL.
- `_AFTER_SEND_ADDR` — проверка ACKSTAT: NACK → ошибка; ACK → по биту R/W: чтение (`RCEN=1`) или запись данных с проверкой WCOL.
- `_AFTER_SEND_DATE` — проверка ACKSTAT на данные (NACK = DATA_ERR, не фатально), затем STOP.
- `_AFTER_SEND_RxEN` — приём байта из SSP1BUF в `value`, затем NACK мастера (последний байт).
- `_AFTER_SEND_NAK` — отправка STOP (ACKEN-последовательность завершена).
- `_AFTER_SEND_STOP` — `do_EXIT()`.

Формальный анализ переходов: все ветки (успех, NACK адрес, NACK данные, WCOL в START/ADDR, BCL) сходятся в единственную точку выхода; мёртвых состояний и недостижимых переходов нет.

## 6. Правила прерываний (инварианты, выработанные в разработке)

1. **ISR — «глупый».** Только проверка PEIE, разрешений и флагов, вызов движка. Никакой логики и обращений к состоянию драйвера.
2. **Флаг потребляется всегда.** Первое действие движка — `I2C_MasterClearIRQ()`, и только потом анализ состояния. Это закрыло рецикл прерывания («выходил и тут же входил»): невыпущенный флаг немедленно перезапускает ISR, вгоняя систему в шторм.
3. **Висячие события глотаются молча.** Если флаг/коллизия подняты, а `state == _IDLE` (транзакции нет), событие съедается без действий. Контракт «state выставляется до взведения железного бита» (в `I2C_Start` порядок: `state`, потом `SEN`) гарантирует, что флаг при idle — всегда хвост, а не работа.
4. **Гвард в I2C_Bus_Error.** Перед записью в дескриптор проверяются `ptr_i2c == 0` и `state == _IDLE`; без гварда висячий BCL дал бы запись по нулевому адресу (порча служебного регистра банка 0).
5. **Трёхуровневая защита дескриптора.** (а) ISR не трогает дескриптор вообще; (б) гвард в Bus_Error; (в) `do_EXIT` обнуляет указатель — после завершения транзакции дескриптора «не существует».

## 7. Восстановление шины

### 7.1 `I2C_Recover()` (аппаратный слой)

Вызывается, когда шина занята (S == 1 или SDA прижата при свободной логике):

1. `SSPEN = 0` — модуль отпускает пины.
2. SDA — вход, SCL — выход; до 9 тактов SCL (разрешение зависшего ведомого, стандартная процедура I2C).
3. Если SDA не отпустилась за 9 импульсов — аппаратная проблема (возврат `false`; помогает только перезапуск питания PCF).
4. Ручной STOP: SDA low→high при SCL = 1.
5. SCL — обратно на вход; сброс хвостовых флагов; `SSPEN = 1`.
6. Контрольная проверка SDA.

### 7.2 Слой приложения (`doRecoveryStep`)

- `Recover()` успешен → ретрай текущего чипа (`doRdUpdate`); шина была грязная, чип не виноват.
- `Recover()` неудачен → `doResetPCF8574()` — аппаратный перезапуск питания PCF8574 (техническая возможность есть; реализация — TODO на следующем этапе).

## 8. Обработчик стека PCF8574 (update.c)

### 8.1 Особенность PCF8574

Порты квазидвунаправленные: вход читается достоверно только если соответствующий бит выходного регистра = 1 (подтяжка «своего»master-слога). Поэтому: **читаем регистр → обновляем тень → пишем `shadow | dir`** (входы возвращаются как 1, выходы — актуальное значение).

### 8.2 Теневая модель

- `shadow_val[8]` — источник истины по каждому чипу (точка фиксации: данные приходят извне и уходят наружу).
- Дескриптор чипа (EEPROM): `adr_chip`, `val_pin` (начальное состояние), `inv_pin` (инверсные пины), `dir_pin` (направления), `btn_pin` (кнопки).

### 8.3 Цикл обновления

```
doRdUpdate   — старт чтения чипа upd_chip (adr = addr<<1 | 1)
doNextRD     — колбэк чтения: анализ ошибки
doCheckUpdate— инверсия inv_pin; разность с тенью; merge тени:
               shadow = (value & dir) | (shadow & ~dir)
               формируем байт записи: value = shadow | dir
               для изменившихся битов — sendState (выходные) / checkPress (кнопки)
doWrUpdate   — старт записи чипа (adr = addr<<1)
doTrailWR    — колбэк записи: анализ ошибки
doCheckExit  — upd_chip++; следующий чип или idle
```

### 8.4 Событийная модель (зафиксированный контракт)

Событие `sendState` описывает изменение **логического** состояния в тени, а не физического регистра чипа. Темпоральная семантика различается по типу пина (определяется `dir_pin`):

- **Входные пины** (физика → логика): событие *подтверждает факт*, который уже случился (мы его прочитали).
- **Выходные пины** (логика → физика): событие *объявляет намерение*, которое станет фактом после успешной записи.

Обоснование выбора: схема самозалечивается при сбое записи. Если транзакция упала, событие уже улетело, но на следующем цикле read покажет старое значение, разность с тенью (тень хранит новое) будет ненулевой → событие повторится → запись ретраится. При «физической» семантике (событие после записи) упавшая запись порождала бы обещанное, но не состоявшееся событие.

Следствие для потребителей: если когда-нибудь понадобится подтверждение «физически записано» — это отдельный канал (крюк уже есть: `exitFunc` вызывается ровно в момент завершения транзакции, `i2c_api.error` говорит, чем она кончилась).

### 8.5 Разбор пинов

Упаковка идентификатора пина (state_pin_t, union):

- Поле `state:2` — состояние (`_DN`/`_UP`); поле `val:1` — значение пина во втором прочтении union.
- Поле `act:1` — тип: величина (0/1) или длительность (короткое/длинное нажатие).

## 9. Фейковый слой для симуляции (i2c_core_sim.h)

Назначение: позволить прогонять полный автомат в симуляторе MPLAB без железа. Перехватывает все функции слоя i2c_core; вместо реальных регистровых операций — модель ведомого:

- `sim_rx` — байт, который «чип» отдаёт на чтение;
- `sim_nack` — true: ведомый отвечает NACK (сценарий ADDR/DATA_ERR);
- `sim_wcol` — true: коллизия записи (сценарий BUFF_ERR).

Сценарии в update.c (сим-конфигурация): чип 3 — «мёртв» (ADDR_ERR), чип 4 — ошибка записи (BUFF_ERR), остальные — нормальный обмен, чтение возвращает 0x5A.

История важной правки: в первой версии фейковый слой не выпускал из прерывания (выходил и тут же входил в него же). Причина — порядок «анализ состояния до потребления флага» в движке; лечение — правило №2 раздела 6 (флаг потребляется всегда, гвард по state после). Правка легла в основу окончательной версии движка.

## 10. Найденные дефекты (ревью 10.11.2026)

### Критичные

| № | Дефект | Лечение |
|---|---|---|
| 1 | Инверсия семантики в фейковом слое: `I2C_MasterTxOK()` возвращал `sim_wcol` напрямую — при ошибке возвращал true («успех»), сценарий чипа 4 в симуляторе не тестировал ничего | `return !sim_wcol;` (одна строка) |
| 2 | Обрезка значения: `_UP = 0x80` в 2-битное поле `state` — всегда записывался `_DN`, `_UP` не существовал | Либо `_UP = 1` (вмещается в 2 бита), либо писать/читать через поле `val` — зафиксировать выбор в этом документе |
| 3 | В `i2c_core.h` отсутствует `I2C_MasterDisableBCL()` (есть только в сим-версии) — реальная сборка не линкуется (I2C_Close её вызывает) | Добавить в i2c_core.h: `PIE2bits.BCL1IE = 0;` |
| 4 | Тупик восстановления: `doRecoveryStep` при успехе ставил `doIdleUpdate`, не трогая `upd_chip` — вечный цикл (в симе маскировался, на железе — до WDT) | При успехе ставить `doRdUpdate` (ретрай текущего чипа) |

### Важные

| № | Дефект | Лечение |
|---|---|---|
| 5 | Блок повторных прототипов в i2c_driver.c: конфликтует с `static inline` из хедера, внутри опечатка (DisableIRQ дважды, DisableBCL ни разу) | Блок удалить целиком |
| 6 | Окно гонки в I2C_Start: висячий флаг между `state = ...` и `SEN = 1` мог запустить движок по START без старта на шине | `I2C_MasterClearIRQ()` в начале I2C_Start (принято как гигиена очереди; осмысленного взводителя в текущей конфигурации нет — страховка на профиль будущих критических секций) |
| 7 | `doResetPCF8574` пуст при живом WDT: зависание без сброса | До реализации — честная заглушка: либо не кормить WDT в этом состоянии, либо явный пустой цикл без CLRWDT |
| 8 | `I2C_MasterDisableIRQ` в аппаратном слое закомментирована («для IRQ режима») — Close наполовину пуст | Раскомментировать (режим выбран: движок из ISR) |

### Замечания по существу (без дефектов)

- Топология автомата и циклы обхода чипов корректны; единственная точка выхода, расходуемый дескриптор, порядок «флаг → гвард → работа» — соблюдены.
- Событие об изменении выходного пина шлётся до физической записи — зафиксировано как осознанный контракт (см. 8.4), а не дефект.

## 11. Конфигурация (config.h) и устойчивость

| Установка | Текущее значение | Рекомендация | Основание |
|---|---|---|---|
| FOSC | INTOSC | OK | Без внешнего кварца |
| WDTE | ON | ON | Контроль зависаний; период задаётся WDTCON (0x12 ≈ 512 мс); SWDTEN при WDTE=ON игнорируется — строка в initWDT закомментирована не случайно |
| PWRTE | OFF | **ON** | Бесплатная страховка чистого старта (сценарий: сброс питания PCF) |
| MCLRE | OFF | ON на время отладки | Ручной сброс кнопкой быстрее цикла «зависло → перепрошил» |
| BOREN | OFF | **ON** | BORV=LO уже задан, но мёртв; BOR даёт предсказуемый сброс при просадке вместо произвольного поведения I2C |
| CLKOUTEN / IESO / FCMEN | OFF | OK | Чисто INTOSC-система |
| CP / CPD / WRT | OFF | По потребности | Защита кода — вопрос политики релиза |
| PLLEN | OFF | OK | 16 МГц достаточно |
| STVREN | ON | OK | Переполнение стека = сброс — на руку при отладке |
| BORV | LO | OK | Низкая точка срабатывания |
| LVP | OFF | OK | Освобождает пин PGM, убирает ловушку «болтающийся провод дёргает порт» |

Примечание по EEPROM: `__eeprom ee_t ee = {...}` с инициализатором поддерживается XC8, но поведение зависит от версии компилятора (в v2.x начальные значения корректно попадают в hex). Если линкер ругнётся — обходной путь: таблица констант во flash + копирование в EEPROM при первом пуске. Проверить на своей версии XC8 до доверия хранилищу.

## 12. Открытые пункты (план)

1. Подтвердить и внести правки по критичным пунктам 1–4 из раздела 10.
2. Подключить таймеры; после этого — полноценно тестировать ветки восстановления (Recover, ResetPCF8574).
3. Добавить таймауты на каждый ход автомата (первым кандидатом — ожидание SSP1IF); обосновать выбор WDT-периода относительно самого длинного цикла main.
4. Реализовать `doResetPCF8574` (аппаратный перезапуск питания PCF).
5. Многое зависит от реального железа: подтяжки, длина шины, ёмкость — перепроверить timing после первого включения.
6. Выбрать и зафиксировать представление `_UP` (см. п. 2 раздела 10) — это часть контракта события для телефонной ветки.

## 13. Резюме для сопровождения

Драйвер построен на трёх принципах, которые важно сохранять при любых правках:

1. **Единственная точка выхода** из транзакции (`do_EXIT`) с расходуемым дескриптором.
2. **Флаг потребляется всегда, работа решается после** — у всех входов движка (ISR, Start, Bus_Error) единый контракт.
3. **Слоение: логика в драйвере, регистры в core-слое, ISR глупый.** Смена железа/симулятора — смена одного файла.

Часть 2 в текущем виде пригодна к передаче в сопровождение с учётом закрытия критичных пунктов раздела 10.
